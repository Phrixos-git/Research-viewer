# Research Viewer

Twitchの日本語配信からゲーム別視聴者数を毎日19・20・21・22・23時（日本時間）に記録し、上位1,000件のライブ配信からゲーム別ランキングと急上昇3選のHTMLを作成します。取得ごとに記録とHTMLをGitHubへpushします。

保存先: https://github.com/Phrixos-git/Research-viewer

ホストPCで動作を確認する場合は、[ホスト側の検証手順](docs/host-verification.md) に従ってください。接続確認、上位最大1,000配信の実取得、保存・HTML・push、23時のメール、定期実行の確認を順に記載しています。

## 初回の設定

必要なものはLinux、Python 3.11以降、Git、systemdです。設定画面にはTkinterが必要です（Ubuntuでは `python3-tk` パッケージ）。

1. Twitch Developer Consoleでアプリを登録します。OAuthリダイレクトURL欄には `https://localhost` を登録し、種類を選べる場合はConfidentialにします。今回の認証はリダイレクトを使わないので、Webサーバーや証明書は不要です。
2. アプリのClient IDとClient Secretを用意します。Secretはチャットに貼ったりGitHubへpushしたりしないでください。
3. このフォルダーで `bash 操作メニュー.sh` を実行すると番号を選ぶメニューが開きます。「1」を選び、設定画面に認証情報を入力して「保存」を押します。以降の接続確認・自動実行登録・結果表示もメニューから選べます。
4. `python3 viewer.py verify` でTwitchから最大1配信を取得できることを確認します。ゲーム配信が含まれない場合も、APIへの疎通は確認できます。
5. このフォルダーをGit Repositoryとして用意し、originを上記URLに設定します。GitHubへはGit自身の認証設定を使います。`git push` を対話なしで実行できるようにしておきます。
6. `python3 viewer.py install-timer` で自動実行を登録します。完了後、日常の操作は不要です。

メニューの起動も含め、初回のGit設定と認証は設定作業として必要です。PythonやGitが設定済みのこの環境を使い、毎回コマンドを入力する運用は行いません。

タイマー登録は現在のユーザーのsystemd設定に書き込みます。収集時刻はこのPCを起動し、ユーザーセッションを稼働させてください。スリープ中や電源OFF中の視聴者数は取得できません。
このPCではタイマーを登録済みで、2026-11-08 19時から毎日19〜23時の取得・push・23時のメール送信が自動で行われています（稼働状況は[検証状況](docs/validation.md)を参照）。

## E2Eテスト

保存済みのテストデータを使う `python3 e2e.py` を用意しています。`--send` を付けた場合だけ `kurahasb@gmail.com` にテストメールを1通送信します。手順と検証範囲は[E2E仕様](docs/e2e.md)を参照してください。

## 正式運用の開始

- 正式取得は **2026-11-08（JST）の19時**から、毎日19・20・21・22・23時に行います。それより前の通常 `collect` は取得・保存・push・通知を行いません。
- 2026-11-07までの記録は全言語のテストデータです。SQLite・JSONと過去HTMLは保存し、HTMLにはテストデータと表示します。正式データへの変換はしません。
- 正式な前日比較・順位変動・メールの再送にはテスト記録を使用しません。11月8日は前日比較なし、11月9日以降に日本語配信同士を比較します。正式取得後のindexは正式データだけから生成します。
- 日本語は配信に設定された言語です。配信者や視聴者の所在地が日本であることを意味しません。

## 結果を見る

HTMLレポートの装飾とメール互換の仕様は[デザイン仕様](docs/report-design.md)に記載しています。
ランキング表では「同時視聴者数」の見出しを数値の上に揃え、数値とバーの間に16pxの余白を設けます。平方根スケールの視聴者数バーと実数を併記し、上位3位をバッジと行背景で強調します。前日比較データがない21時・23時のHTMLは空の比較セクションを表示せず、「前日比較データは蓄積中です」とまとめます。冒頭に日時（曜日付き）と、1位タイトル・タイトル数・ゲーム集計対象配信数の3枚の要約タイルを表示し、収集開始・終了時刻はフッターに記載します。増減の数値は上昇を赤系、下降を青系で色分けし、5件未満の部分集計の比較件数は琥珀色で示します。

`output/index.html` をブラウザで開いてください。手動で開く場合は `python3 viewer.py open` も使えます。
21時・23時には `output/YYYY-MM-DD/21.html` と `23.html` に前日比較を残します。
GitHub上のHTMLファイルはソースとして表示されます。ダウンロードして開いてください。
ランキング表は幅100%・自動レイアウトで、ゲームタイトル列が残りの幅を使い、長いタイトルは折り返します。順位・数値の列は折り返しません。

## 集計のルール

- 日本語（配信言語 `ja`）のライブ配信をTwitchの視聴者数順にたどり、配信IDの重複を除いて最大1,000件を取得します。1,000件未満で一覧が終われば、取得できた分だけを使います。0件も正常な取得として保存します。
- 上位1,000件の枠は雑談・カテゴリ未設定を含む日本語配信全体です。その枠の中から、従来どおりTwitchにIGDB IDが登録されているゲームの配信を抽出し、ゲームID別に視聴者数を合計します。除外した配信を埋めるための追加取得はしません。
- ランキング表とメールのタイトル一覧は上位100タイトルまで表示します。取得・集計・SQLite・JSONには対象ゲームをすべて保持します。HTMLでは表示件数と集計件数を区別し、配信取得件数とゲーム集計に使った配信件数も残します。23時のランキング表には前日の23時からの順位変動（-：同順位／↑：上昇／↓：下降／★：前日に同じゲームIDがない）を右端に表示します。前日の101位以下も比較対象に含め、前日の記録自体がない場合も★とします。
- 数値は上位配信の範囲内の合計であり、そのゲームの全配信の合計やユニーク人数ではありません。ページ取得中の配信状態・順位の変化により、完全に同時刻の上位1,000件は保証できません。
- 通信に失敗した回は成功データとして記録しません。途中の数値を0で埋めることはありません。
- 通常の急上昇3選は、同じ日の直前1時間の記録と比べた増加人数順です。19時や欠測時は比較なしです。
- 21時は両日の19・20・21時、23時は両日の19〜23時を比較します。ゲームごとに両日に存在する同じ時刻の組だけを平均し、平均同時視聴者数・増加人数・増加率を表示します。集計期間内の推定ユニーク視聴者数ではありません。
- 比較件数と予定件数を併記します。取得した配信の範囲外のゲームは未取得として扱い、0人とは見なしません。前年ではなく前日と比較し、前日データがなければ「比較データなし」です。
- 急上昇は全体で25％以上増加したタイトルを対象に、最多寄与配信者を両時点から除いても25％以上増加する「通常の急上昇3選」と、それ以外の「単一配信者による急増」に分けます。各時間帯・各枠で増加人数順に最大3件。全体で25％以上増加したタイトルのうち、配信者別内訳が未取得のものは推測せず判定不可とします。比較元0人からの増加は増加率を算出できないため、急上昇・判定不可のどちらにも数えません。通常ランキングや平均人数の比較は変えません。詳細・0人の扱いは[配信者別の判定仕様](docs/streamer-rises.md)に記載しています。
- 21時・23時のHTMLは、各時間帯の前日比較（急上昇・単一配信者枠・判定不可注記）を表示せず、期間平均の前日比較表を表示します。メールHTML本文・添付も同じです。メールのテキスト本文では従来どおり時間帯別に最大3件を選出します。
- 23時のタイトルランキングは、右から2列目に「19〜23時平均の前日増減（人）」を表示します。両日に同じゲームID・同じ時刻がある組だけで平均を比較し、符号付き小数1桁と比較件数/5を表示します。欠測は0で補完せず、比較できないタイトルは「比較データなし」、5件未満は部分集計とします。他の時間にはこの列を表示しません。
- 23時の期間平均比較表は増加率順のTop10（同率はゲームID順）です。比較元0人で率が算出できないタイトルを除き、減少・横ばいも含めて最大10件を表示します。タイトルランキングの平均増減列は全タイトル分を保持し、順位前日比の↑は赤系、↓は青系、★は黄色で表示します。
- 同じ予定時刻の再実行は既存の記録を再利用します。重複収集・上書きはしません。タイマーは開始が予定時刻から10分以上遅れた回を欠測にします。
- pushは取得・集計完了後です。予定時刻ちょうどのpush完了を保証するものではありません。

## 保存と障害時の動作

認証情報は `.local/config.json`（Git管理外、所有者だけ読み書き可）に保存します。アクセストークンはメモリー内で使い、保存しません。
取得記録の正本は `.local/viewers.sqlite3` です。Python標準のSQLiteを使うため、データベースサーバーのインストールは不要です。
比較とHTML生成はSQLiteに保存した記録を読み取って行います。履歴の自動削除は行いません。

| テーブル | 項目 |
|---|---|
| `collection_runs`（取得した回） | `id`、`scheduled_at`（予定日時・重複禁止）、`started_at`、`finished_at`、`stream_count`（取得配信数）、`included_stream_count`（ゲーム集計対象の配信数） |
| `viewer_counts`（ゲーム別視聴者数） | `run_id`、`game_id`（TwitchゲームID）、`game_title`、`viewer_count` |
| `game_audiences`（取得した配信者別内訳） | `run_id`、`game_id`、`counts_json`（Twitch配信者ID別の人数辞書） |

日時は日本時間のオフセット付きISO 8601形式で保存します。同じ取得回・ゲームIDの組は重複禁止で、視聴者数は0以上の整数です。
配信数と取得回・全ゲームの記録は1つのトランザクションで保存します。途中失敗時はその回全体を取り消します。
タイトル名は各取得時点の名前を残し、比較ではゲームIDを使います。

GitHub向けにSQLiteから `data/YYYY-MM-DD/HH.json` を出力し、HTMLは `output/` に保存します。
SQLite本体と一時ファイルは `.local/` 内に置き、Gitへ追加しません。データベース保存後にJSONやHTML出力が失敗しても、次の実行で保存済みの記録を使って出力し直します。
通常実行でJSONを読み込んだり、旧保存方式から自動移行したりする処理はありません。全配信集計だった旧データと新方式の数値は比較できません。旧DB・JSONは自動変換せず、必要ならタイマー停止後に別の場所へ保管し、新方式の履歴を新規に記録してください。既存データをこの変更で削除する処理はありません。

SQLiteを失った場合は、GitHubからJSONを取得したうえで `python3 viewer.py restore` を実行すると、空のデータベースへ履歴を復元できます。操作メニューの「7」からも実行できます。
復元はすべてのJSONを1つのトランザクションで読み込みます。不正・重複があれば全体を取り消し、記録が入っているデータベースは上書きしません。
SQLiteに正式期間（2026-11-08以降）の記録が1件もないのに、正式期間のJSONが `data/` にある場合、通常の収集は復元を促して中断します。テスト期間（2026-11-07まで）のJSONだけがある場合は中断せず、そのまま正式取得を始めます。

## 23時のメール通知

毎日23時の記録を保存・HTML出力した後、その回の前日比較・上位100タイトルをメールで通知できます。テキスト本文には時間帯別の急上昇3選も含めます。19〜22時のレポートはメール送信しません。
メールにはテキスト本文とHTML本文を含め、出力したHTMLそのものもファイルとして添付します。メールソフトでレイアウトが変わる場合は、添付HTMLをブラウザで開いて確認できます。前日データがない場合も、その旨を記載したレポートを送ります。
配色はライトテーマ（ペーパー）で、背景はHTMLとメール本文の両方で明るいグレー `#f6f7f9`、表やタイルの面は白 `#ffffff`、文字は濃い紺 `#1c2230` にします。色は `viewer.py` の配色定数（`BG`・`INK` など）にまとめています。メールソフトがhead内のCSSを省略しても読めるよう、本文・外枠テーブル・セルにインライン指定と背景色属性を設定します。メールソフト独自のダークモードによる色変更は、受信側で確認します。
HTML本文と添付HTMLは表示領域の幅（最大960px）に合わせ、長いゲーム名を折り返します。数値・順位は桁の途中で折り返しません。幅600px以下では前日比較をタイトルごとのカード（2列）にし、ランキングの順位列を細くして余白を小さくします。head内のCSSを省略するメールソフトでは、外枠・比較表・ランキング表は幅100%、色・タイル・セルの折り返し指定はインラインで表示します。実際の表示はメールソフトのCSS対応に依存するため、受信画面でも確認してください。保存済みの `output/index.html` と2026-11-05・2026-11-06の21時・23時HTMLも保存済みJSONから再生成しました。送信済みメールの本文・添付HTMLは変更しません。

操作メニューの「8」（`python3 viewer.py setup-mail`）で、送信用Gmailアドレス・アプリパスワード・複数の宛先を入力し、有効にして保存します。宛先は改行またはカンマで区切れます。
Gmailの `smtp.gmail.com:465` にSSL/TLSで接続し、宛先ごとに個別に送信します。他の宛先はメールに記載しません。
アプリパスワードの発行にはGoogleアカウントの2段階認証が必要です。アカウントの種類・設定によって発行できない場合があります。[Google公式手順](https://support.google.com/accounts/answer/185833?hl=ja)
通常のGoogleログイン用パスワードは使用しません。設定保存時にはメールを送信しません。
設定は `.local/mail.json` に所有者だけが読み書きできる権限で保存し、宛先やアプリパスワードをGitHubへ出力しません。未設定・無効の場合は収集だけを行います。

送信履歴はSQLiteの `mail_deliveries` テーブルに取得ID・宛先・状態・試行日時・SMTP受付日時を保存します。状態は `pending`（未送信）、`sending`（送信開始）、`sent`（SMTP受付済み）、`failed`（未送信と確認できた失敗）、`uncertain`（受付されたか不明）です。
SMTP受付済みの同じ回・同じ宛先には再送しません。複数宛先のうち一部が失敗しても、成功した宛先には再送しません。`sent` は宛先の受信箱への到着を保証するものではありません。
接続・認証の失敗など、送信されなかったことが確認できる場合は、次の23時の実行時に再試行します（同じ23時の回を手動で再実行した場合も対象です）。設定から削除した宛先へは自動再送しません。
送信中の切断や送信履歴更新前の中断で受付状況が不明な場合（`sending`・`uncertain`）は、自動再送せず状態を残します。SMTPとSQLiteをまたいだ厳密な一度だけの送信は保証できません。
状態はメニューの「9」（`python3 viewer.py mail-status`）で確認できます。送信履歴・宛先はJSONに含めないため、JSONからSQLiteを復元しても送信履歴は復元されません。

GitHubへのpushとメール通知は独立して実行します。push失敗時も保存済みレポートの送信を試みます。メール送信の失敗でSQLiteの記録を取り消すことはありません。
設定を有効にする以前の過去レポートを一括送信することはありません。送信サービス・宛先・認証設定が完了するまで、実メールの動作確認は行えません。

収集はロックで重複を防ぎ、Gitへ追加するのは `data/` と `output/` だけです。無関係な変更やステージ済みの変更があればpush作業を中断します。force pushや自動mergeは行いません。
push失敗時も記録とcommitを保持し、次回に再送します。自動処理のログは `journalctl --user -u research-viewer.service` で確認できます。ログにSecretやトークンは出しません。

停止: `systemctl --user disable --now research-viewer.timer`

開発テスト: `python3 -m unittest discover -s tests -v`

API取得可否の調査記録は [docs/twitch-feasibility.md](docs/twitch-feasibility.md) を参照してください。
